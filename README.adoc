`rtc2gitcli` migrates the source control history of https://www.ibm.com/products/engineering-workflow-management[IBM Engineering Workflow Management (EWM)], formerly Rational Team Concert (RTC), into Git.
It is a plugin for IBM's `scm` command line that adds the subcommand `migrate-to-git`. It was inspired by https://github.com/rtcTo/rtc2git[rtc2git].

The plugin replays a stream's history in an `scm` sandbox. It accepts one change set at a time into a target workspace and commits the result with https://www.eclipse.org/jgit/[JGit]. Every Git commit is therefore exactly what `scm load` writes for that point in the history.

== What it migrates

[cols="1,2"]
|===
|EWM |Git

|Change set
|One commit, even when only properties changed. Author and dates come from EWM, the comment and work items form the message (configurable), and an `EWM-ChangeSet: <uuid>` trailer links back to EWM.

|Delivery order
|Commits follow the order in which each component received its change sets, not their creation order.

|Baselines, snapshots
|Annotated tags (filtered by name), with the EWM UUIDs in the tag message.

|Streams
|One branch per stream in one repository. A branch starts where its history leaves the branches already migrated. See link:docs/streams-as-branches.md[].

|Line delimiters, binary content types, executable flag
|A generated `.gitattributes` block and the file mode, so a checkout reproduces `scm load` byte for byte.

|`.jazzignore`
|`.gitignore`. Files that EWM versions despite an ignore pattern are committed anyway.

|Empty folders
|Optional `.gitkeep` files (`keep.empty.folders`).

|Large files
|Optional Git LFS (`lfs.threshold`, `lfs.patterns`).

|z/OS language and data set definitions, build variables, code pages
|`.ewm/zos-metadata.json` and `zos-working-tree-encoding` attributes. A DBB zBuilder configuration is generated from them. See link:docs/zos-migration.md[].
|===

== Requirements

* *EWM 7.2 SCM Tools* (the `scm` command line, from the EWM download page). The 7.2 tools run on Java 17.
** On Apple silicon without Rosetta, the bundled x86_64 JRE does not start. Run `eclipse/plugins/org.eclipse.equinox.launcher_*.jar` with a local Java 17 instead, as the `eclipse/scm` script does.
** z/OS migrations need the SCM Tools *with Enterprise Extensions*. `tools/assemble-ee-scmtools.sh` builds them from the EWM Build System Toolkit repository.
* A user who can read the streams and create repository workspaces.
* For the z/OS tooling: the git command line, Python 3.11+ with https://docs.astral.sh/uv/[uv], and Apache Ant (only to export the system definitions).

== Build and install

The `com.ibm.team.*` bundles are not on Maven Central. The build uses a local SCM Tools copy as its target platform:

[source,bash]
----
export SCMTOOLS_HOME=<scmtools>              # folder that contains eclipse/plugins
./mvnw verify                                # compile, run the tests, build the bundle
tools/install-scmtools-plugin.sh <scmtools>  # register the bundle in that SCM Tools copy
<scmtools>/eclipse/scm help migrate-to-git
----

EWM 7.x starts its bundles through `simpleconfigurator`, so the plugin must be registered in `bundles.info`; the `dropins/` folder is ignored. The install script does this. That also fixes the old "unknown subcommand" problem of RTC 6 and later.

== Migrate a stream

Log in once and let `scm` keep the credentials. No password appears on later command lines:

[source,bash]
----
scm login -r https://ewm.example.com:9443/ccm -u <user> -n ewm -c
----

Then migrate. `--stream` creates the two repository workspaces the migration needs if they do not exist yet:

* a *source* workspace that flows with the stream;
* a *target* workspace that starts at each component's initial baseline.

It then loads the target workspace into the sandbox:

[source,bash]
----
mkdir -p sandbox/.jazz5        # a new sandbox needs an empty .jazz5 folder for -d
scm migrate-to-git -r ewm -m migration.properties --stream "My Stream" -b main -d sandbox \
    my-stream-source my-stream-target
----

The Git repository is the sandbox itself. Push it when the migration is done:

[source,bash]
----
git -C sandbox remote add origin <url>
git -C sandbox push origin --all && git -C sandbox push origin --tags
git -C sandbox lfs push --all origin    # only with lfs.* enabled (needs git-lfs)
----

Before migrating, `-L` lists the baselines and change sets without changing anything.

To use workspaces you set up yourself, leave out `--stream`, load the target workspace with `scm load` and run `migrate-to-git` inside that sandbox. The target workspace must flow with the source workspace and contain the components at the state the history should start from.

=== Options

[cols="1,3"]
|===
|`-r`, `-u`, `-P`, `--certificate`, ... |The usual `scm` login options. Prefer a nickname from `scm login -c`.
|`-m <file>` |Migration properties. link:migration.properties[] documents every property with its default.
|`--stream <name>`, `-S` |Create the workspaces from this stream and load the target workspace (see above).
|`-d <dir>` |The sandbox. Required with `--stream` for a new sandbox.
|`-b <branch>` |The branch to commit to: the initial branch of a new repository, or the new branch with `-g`.
|`-g <sandbox>` |Add this stream as a new branch to the repository of an earlier migration (see link:docs/streams-as-branches.md[]).
|`-L` |List the tags and change sets that would be migrated, then stop.
|`-t <seconds>` |Repository connection timeout (default 900).
|`-U` |Update migration: skip a leading empty tag.
|===

=== Interrupting, resuming and updating

Run the same command again to continue a migration or to bring the repository up to date with new deliveries, for example until the cut-over:

* Change sets that already have a commit are recognized by their `EWM-ChangeSet` trailers.
* A run that stopped between accepting a change set and committing it is detected; that change set is discarded and migrated again (`resume.discard.pending`).
* A sandbox with uncommitted changes is refused.

Every run writes a JSON report (`.git/rtc2git/report-<time>.json`) listing the migrated change sets, tags, warnings and, for a branch, its branch point.

=== Checking the result

link:docs/e2e-testing.md[] describes how the plugin was tested against an EWM 7.2 server:

* comparing `git archive` with `scm load`;
* checking one commit per change set;
* killing a run and resuming it.

== Several streams

Migrate the main stream first, then each other stream into its own sandbox with `-g <first sandbox> -b <branch>`. All streams end up as branches of one repository. link:docs/streams-as-branches.md[] explains how the branch points are found and what happens to change sets that several streams share.

== z/OS and DBB zBuilder

For EWM z/OS projects (Enterprise Extensions), the migration carries over:

* the language definition of every member;
* the data set definition of every zFolder;
* file-level build variable overrides and code pages.

The `ewm2zbuilder` Python tool in link:ewm2zbuilder[] turns them, plus an export of the project area's system definitions, into a DBB zBuilder configuration:

* a shared build configuration (`Languages.yaml`, one language task per compiler; CICS, Db2 and link-edit variants merged into one task);
* a `dbb-app.yaml` in the application repository, with the `zOSsrc` folders renamed to `src`.

[source,bash]
----
tools/export-sysdefs -t <buildtoolkit> -r <uri> -u <user> -p "<project area>" -o sysdefs.xml  # asks for the password
scm migrate-inventory -r ewm -o inventory.json "<stream>"   # what the stream uses, before migrating
tools/migrate-zos -r ewm -s "<stream>" -x sysdefs.xml -w work -t app-repo -c <zBuilder schema.json>
----

See link:docs/zos-migration.md[] for the flow and the mapping rules, and link:docs/ewm-zos-model.md[] for how EWM stores this metadata.

== Limitations

* EWM does not record merges, so the branches have no merge commits. A change set delivered to several streams becomes a commit on each branch, with the same `EWM-ChangeSet` trailer.
* Work items are carried only as numbers and summaries in commit messages. Linking the commits back to EWM work items through the Git Server Toolkit is a separate step.
* The z/OS output has been validated against the zBuilder schema, but not yet built with DBB.
